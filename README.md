# MaaBaseOptimizer

一个面向明日方舟基建的本地排班分析器。支持 `2-4-3`、`1-5-3` 和 `3-3-3` 左侧布局，读取森空岛或 MAA `OperBox` 的干员识别结果，根据精英阶段解锁后勤技能，同时生成两套互斥班组、一个不重复的轮班循环和 24 小时收益曲线。

## 先说结论：它与 MAA 默认换班有什么不同

MAA 默认基建换班计算的是**单设施最优**：进入一个房间后，识别当前可用干员的后勤技能，比较普通加成和已配置的特殊组合，选出该房间的最高分组合。它不会为了后面的另一个房间保留某名干员，也没有把控制中枢、宿舍、制造站和贸易站放进同一个全局目标。

本项目采用两层模型：

1. 枚举每种产物下的高价值三人房间组合；
2. 保留生产状态不同的控制中枢候选（例如木天蓼、深海猎人、全贸易站效率），分别求解其下游房间；
3. 将房间组合放入 0-1 整数规划，同一干员全局最多出现一次，每类房间必须选够指定数量，再按最终资源目标比较控制中枢方案。

因此这里求的是候选组合范围内的跨房间协调解，而不是依次给每个房间做贪心选择。安装 PuLP 时，CBC 能证明“已经保留的候选组合”内的单班分配最优；它不能证明完整干员组合、A/B 两班、心情恢复和时间轴联合问题的全局最优。缺少依赖时自动退回候选集协调搜索。

候选目标有两种口径。默认“固定产品布局：总产能等权最大化”，用户选择的贸易站/赤金站/经验站数量和产品类型是硬约束，各类房间按无加成基准日产归一后等权处理；可选“固定产品布局：一图流等效理智最大化”，使用默认钱书价值比 `229/145` 和无人机一般等价物口径处理跨设施干员竞争。等效价值不会改变房间产品配置，只改变多个房间争抢同一干员时的取舍。程序会把两种目标各自生成的完整 A/B 方案再次按两套评分交叉比较；若某个方案同时占优，两种目标返回同一排班是合法收敛，并会在结果页逐房间解释被淘汰候选。

产出规划使用解析期望快速比较候选；“随机快进”使用独立的离散事件模拟器在同一虚拟时间线上重放物理房间的 A/B 班次、逐件制造、逐笔订单、仓库满载和实际上线节点。未完成进度跨班保留，收菜时先收制造产物再交订单，无人机逐架减少三分钟基础工时。统计按完整排班的试验结果计算，固定种子可复现。界面另有每 15 分钟积分的解析曲线，两者用途不同。

2026-09-14 更新：小于 8 小时的上线间隔默认仅在 06:00–24:00 内操作，06:00 可换班，午夜不换班；8/12 小时方案保持原时序。跨午夜的同一班不会重置技能暖机或心情。材料余额不限制生产，允许每日赤金净减少设置保留。该次计算更新未修改前端。详见 [上线与心情校对](docs/login-morale-2026-09-14.md)。

前一轮更新与公式来源、模拟边界及验证方法详见 [2026-09-13 校对报告](docs/production-audit-2026-09-13.md)。国服目录已同步至 2026-09-11 的客户端 2.7.71，包含 429 名基建干员和 755 条技能。可运行 `.venv/bin/python scripts/update_catalog.py` 获取后续版本；新增机制仍需公式审计。

制造站技能按结算层级处理。冬时的“科学改造/流程优化”以及自动化类技能会先清除同站干员提供的普通生产力，之后只保留明确写作“根据设施数量提供加成”的效果；仓库容量以及红云/泡泡的仓容转换不属于设施数量，因此不会在冬时 + 红云 + 火神组合中被错误恢复。干员阵营、小队和术语成员来自目录数据与 `data/riic_terms.json`，不再把相似名称或共用技能图标当成同一机制。

可运行全目录技能审计：

```bash
.venv/bin/python scripts/audit_skills.py
```

审计会检查干员技能槽引用、游戏数据到 MAA 图标的映射、同图标不同技能条目以及本地公式覆盖。未完整建模的条件技能会继续明确列为“部分覆盖”，不会宣称全游戏 100% 精确。

可以固定一名群体恢复干员常驻宿舍。该干员会从生产候选中移除，并按“占用 1 张床、强化同宿舍其余 4 张床”进入恢复审计，而不是把技能错误地作用于全部 20 张床。

菲亚梅塔是目录级机制，不依赖开发者自己的 Box：拥有并启用时，她固定占用一个宿舍位，B 班候选允许一个 A 班生产目标在不重叠的时间段继续工作。仅在上线且自身回满时按“患难之交”互换心情，并检查菲亚梅塔以 `2 心情/小时` 能否在下次换班前回满；不满足就禁止该时间状态。未拥有时只显示“支持但未激活”。

## 当前使用的产出模型

- 赤金：无加成时每 72 分钟 1 根，即每个制造站 20 根/日。
- 中级作战记录：无加成时每 3 小时 1 份，即每个制造站 8000 经验/日。
- 源石碎片：基础 60 分钟 1 份；固源岩配方每份消耗 2 固源岩与 1600 龙门币，装置配方每份消耗 1 装置与 1000 龙门币。
- 源石订单：基础 120 分钟，交付 2 个源石碎片获得 20 合成玉；碎片制造和订单消耗分别计入库存流。
- 三级贸易站的 2/3/4 赤金订单概率为 30%/50%/20%，基础时长为 144/210/276 分钟；据此计算长期平均龙门币和赤金消耗。
- 每名处于工作状态的制造/贸易干员提供 1% 基础效率；每名发电站干员提供 5% 基础充能速度。
- 无基础充能加成时每 6 分钟恢复 1 架无人机，每架减少 3 分钟制造或订单基础工时，不再额外乘干员生产倍率。
- 发电站每名在岗干员的 5% 基础充能和后勤技能充能会先在三个发电站求和，再换算成无人机实时恢复速度。库存上限按 235 架处理；无人机只在页面设定的 2/4/6/8/12 小时上线节点投入，不再把整日加速平滑摊进每一分钟。
- 自动分流把用户填写的“允许赤金库存净变化/日”作为库存目标。它可以是负数，用于表达签到、活动、信用商店和已有库存对赤金缺口的补贴；模型比较当班赤金制造与贸易房间的每架无人机边际流量，只投达到目标所需的最少无人机给赤金，其余投入贸易。固定全投某类房间仍可作为对照。
- 结果侧栏拆分显示无人机的基础 240 架、发电站增幅、每班实际分流与目标资源增量；24 小时图显示“当前无人机库存”的锯齿变化和每个投入节点，而不是没有操作含义的累计恢复直线。
- 普通技能取游戏 `building_data.json` 的解锁条件与数值；经典组合可采用 MAA 的组合分辅助候选排序，但资源流只使用本项目明确实现的机制规则。

特殊效果不按干员姓名写分支。`maabase/mechanics.py` 以技能 buff 图标识别机制，多个干员若共享同一机制会自动复用同一条规则。当前贸易订单规则覆盖订单品质、违约订单、四赤金订单投资和“低语”的效率替换。新增干员通常不需要改程序；只有游戏加入一种从未出现过的状态量或结算规则时，才需要新增一种机制处理器。

`maabase/state_model.py` 维护跨设施状态图，目前包含：控制中枢全贸易/制造加成、木天蓼、制造配方种类、赤金生产线、发电站作业平台、仓容转换、同站条件、心情落差、工作时长、人间烟火、感知信息、思维链环、巫术结晶、无声共鸣、工程机器人、魔物料理和热情值。结果页会显示本次方案实际触发的公式。

结果页采用生产监控台布局，并参考一图流 `scheduleV3` 的“数据来源 → 设施配置 → 排班预览 → 执行/验证”分步结构。主区按房间展示不重复的 24 小时轮班；头像角标显示当前精英阶段，技能图标悬浮显示完整说明与解锁阶段，无人机图标直接标在实际加速的设施条上。累计收益与实时速率使用随应用本地发布的 Apache ECharts，支持悬停、缩放、图例和浅色/深色主题重绘。头像与技能图标按 PRTS 资源标识加载，加载失败时自动隐藏，不影响计算。

随机快进使用完整房间时间线，不再分别模拟 A/B 后加权分位数。材料始终视为有外部补给，负库存用于显示消耗缺口；兼容旧界面的严格库存选项，但不再按材料余额停产。输入固定随机种子可重现每轮轨迹，留空则使用新种子。页面提供前 48 小时收取账本与完整结果 JSON 下载；明细最多记录前 2000 个完成事件，统计不截断。心情、床位和产出在同一时钟内推进，跨日不重置；心情归零使相关加成失效，保留岗位至合法上线时刻。品质暖机等近似详见校对报告。

制造站的赤金、作战记录、源石碎片数量可以任意合法组合；源石订单贸易站从零到布局上限独立选择。合成玉由贸易站消耗碎片获得。高级设置可按固源岩/装置搓玉成本给合成玉定价，并填写材料理智价值；完整经济评分扣除材料与龙门币成本，计入剩余碎片净值，避免中间品重复估价。

界面与求解行为对照了 [一图流前端](https://github.com/Arknights-yituliu/frontend-v2-plus) 的 `riic-schedule-generator.vue`、[一图流后端](https://github.com/Arknights-yituliu/BackEndV3)、干员-作业匹配工具和 PRTS.plus。参考项目的排班页本身是约 1.05 万行的 Vue 单文件页面；本项目没有直接复制该文件或混入其状态，而是复用分步工作流、独立班次设置、执行节点和排班预览这些交互概念，继续保留本项目的本地 Python 求解与详细资源流审计。

订单品质的解析层使用班内暖机积分后的平均分布，随机快进按每笔订单开始时的在岗时长取样；长订单与收取边界可能使两者产生系统性差异，不能只靠增加试验次数消除。

界面保留每日赤金净流下限，外部赤金收入与原材料库存无需填写；API 继续支持外部来源输入。搓玉消耗的龙门币按完成的碎片数量扣除，净收入为赤金贸易收入减去搓玉消耗。

订单品质不会直接套用峰值。PRTS 已给出 α/β 的峰值概率和分别 3/5 小时达到峰值的时间，但没有公开完整内部曲线，因此解析层对峰值前采用线性插值，并积分成班均订单分布；快进层逐单使用相应时刻的概率。该假设会明确显示，不会标成官方精确曲线。

## 为什么显示“保守估算”

现代后勤技能有大量跨房间状态量，例如感知信息、思维链环、人间烟火、巫术结晶、红松骑士团、设施内特定阵营人数、订单品质暖机和特殊订单。这些效果不可能只用“+X%”准确概括。

当前版本会：

- 精确处理直接效率技能；MAA 已建模技能组只辅助候选排序，不冒充精确资源流；
- 将含“每有/如果/转化/工作时长”等条件、但仅能读取直接数值部分的技能明确标为“仅计直接部分”；
- 将未完整建模的特殊技能列在警告中；
- 不把结果伪装成游戏内逐秒模拟值；
- 用满级宿舍的 `4 心情/小时` 基础恢复，按床位小时审计一班休息能否回满；审计额外计入控制中枢、会客室、办公室共 8 个辅助岗位；
- 生成两套带时间边界的班组；普通干员严格互斥，只有菲亚梅塔指定的单一目标可在心情交换审计通过后出现在相邻的非重叠班次。

工时搜索先以恢复量和床位小时筛选；最终另做连续 7 日、20 张床位的心情重放。床位仅在上线时重新分配，心情回满不会触发离线腾床。控制中枢和跨房间依赖会同步切换；宿舍、办公室和会客室仍需进一步纳入联合多班次状态求解，才能闭合所有依赖这些设施的人间烟火、感知信息等状态链。

页面会对每个房间同时展示“实际在岗时长”和“该组合自身的上线节点对齐安全上限”。例如古米/月见夜/空爆三人的交际技能会得到 `0.40 心情/小时`（五人中枢减耗 0.25、同站三人减耗 0.10、自身技能减耗 0.25）；在每 2 小时可上线的设置下，如果它比替班组合更强，房间求解器会在恢复约束允许时让它多工作一个或多个 2 小时时段。24 小时周期同时约束另一班必须获得足够工作与恢复时间，因此不会简单把单队拉满到其孤立安全上限。

贸易站公式已用 BioHazard 的三级站数据建立回归表，覆盖常规、裁缝 α/β、但书 II、龙舌兰 II 以及它们的 10 种组合。单位基础工时的龙门币和赤金结果逐项一致；班次内裁缝暖机则作为在该稳态表之上的显式时间模型单独计算。

程序会同时生成“本次 Box 激活情况”和“全干员各解锁阶段目录能力覆盖率”，Box 只决定机制是否激活，绝不决定程序是否实现它。孑的订单队列空位按界面选择的收单间隔做稳态队列期望，进行中的订单在收单时保留进度；歌蕾蒂娅的深海猎人加成会按所有已选制造站中的深海猎人总数回代一次。审计现覆盖 337 项产出相关技能版本，包含会被精英化替换的低阶段技能；新数据引入未解释机制时，审计继续报告缺项。
