# MaaBaseOptimizer

一个面向明日方舟基建的本地排班分析器。支持 `2-4-3`、`1-5-3` 和 `3-3-3` 左侧布局，读取森空岛或 MAA `OperBox` 的干员识别结果，根据精英阶段解锁后勤技能，同时生成两套互斥班组与 48 小时循环运行图。

## 先说结论：它与 MAA 默认换班有什么不同

MAA 默认基建换班计算的是**单设施最优**：进入一个房间后，识别当前可用干员的后勤技能，比较普通加成和已配置的特殊组合，选出该房间的最高分组合。它不会为了后面的另一个房间保留某名干员，也没有把控制中枢、宿舍、制造站和贸易站放进同一个全局目标。

本项目采用两层模型：

1. 枚举每种产物下的高价值三人房间组合；
2. 保留生产状态不同的控制中枢候选（例如木天蓼、深海猎人、全贸易站效率），分别求解其下游房间；
3. 将房间组合放入 0-1 整数规划，同一干员全局最多出现一次，每类房间必须选够指定数量，再按最终资源目标比较控制中枢方案。

因此这里求的是候选组合范围内的跨房间协调解，而不是依次给每个房间做贪心选择。安装 PuLP 时，CBC 能证明“已经保留的候选组合”内的单班分配最优；它不能证明完整干员组合、A/B 两班、心情恢复和时间轴联合问题的全局最优。缺少依赖时自动退回候选集协调搜索。

现在的产出计算采用“解析期望 + 离散事件”混合模型：协调器使用解析期望快速比较候选，快进工具再逐笔生成贸易订单、逐件完成制造产品。A/B 两队完全互斥；默认让每队尽量工作到心情阈值前，并在制造与贸易的统一收取节点换班，连续工作上限可设为 8/12/16/24 小时。离岗后按 20 张床和满级宿舍基础恢复速度审计能否在下次上班前回满。芬、克洛丝等整点变化技能先分阶段积分，再用于班次产出。

## 导入自己的 Box

点击“导入 MAA 识别结果”，选择包含 `own_opers` 的 MAA `OperBox` 回调 JSON。程序允许 `own_opers` 位于根对象、`details`、`data`、`result` 或回调数组中。最小格式见 `examples/operbox_sample.json`。

每一项需要这些字段：

```json
{
  "id": "char_002_amiya",
  "name": "阿米娅",
  "elite": 2,
  "level": 50,
  "potential": 6
}
```

其中潜能不影响后勤技能，目前仅保留以兼容 MAA 输出。也可以在界面中按名称手动补充干员并修改精英阶段、等级。

## 当前使用的产出模型

- 赤金：无加成时每 72 分钟 1 根，即每个制造站 20 根/日。
- 高级作战记录：无加成时每 3 小时 1 份，即每个制造站 8000 经验/日。
- 源石碎片：基础 60 分钟 1 份；固源岩配方每份消耗 2 固源岩与 1600 龙门币，装置配方每份消耗 1 装置与 1000 龙门币。
- 源石订单：基础 120 分钟，交付 2 个源石碎片获得 20 合成玉；碎片制造和订单消耗分别计入库存流。
- 三级贸易站的 2/3/4 赤金订单概率为 30%/50%/20%，基础时长为 144/210/276 分钟；据此计算长期平均龙门币和赤金消耗。
- 每名处于工作状态的制造/贸易干员提供 1% 基础效率；每名发电站干员提供 5% 基础充能速度。
- 无基础充能加成时每 6 分钟恢复 1 架无人机，每架减少 3 分钟制造或订单时间。
- 发电站每名在岗干员的 5% 基础充能和后勤技能充能会先在三个发电站求和，再换算成每日无人机；无人机投向会进入对应房间的额外倒计时时间。
- 普通技能取游戏 `building_data.json` 的解锁条件与数值；经典组合可采用 MAA 的组合分辅助候选排序，但资源流只使用本项目明确实现的机制规则。

特殊效果不按干员姓名写分支。`maabase/mechanics.py` 以技能 buff 图标识别机制，多个干员若共享同一机制会自动复用同一条规则。当前贸易订单规则覆盖订单品质、违约订单、四赤金订单投资和“低语”的效率替换。新增干员通常不需要改程序；只有游戏加入一种从未出现过的状态量或结算规则时，才需要新增一种机制处理器。

`maabase/state_model.py` 维护跨设施状态图，目前包含：控制中枢全贸易/制造加成、木天蓼、制造配方种类、赤金生产线、发电站作业平台、仓容转换、同站条件、心情落差、工作时长、人间烟火、感知信息、思维链环、巫术结晶、无声共鸣、工程机器人、魔物料理和热情值。结果页会显示本次方案实际触发的公式。

结果页采用生产监控台布局：主区首先按房间展示 48 小时运行图，色块内直接列出当班干员，悬停查看技能、效率与结束心情；随后列出 A/B 两套房间安排。固定侧栏展示每个跨房间状态的来源、实际受益房间及贡献百分点。页面会对 A/B 两队分别执行一次 30 天 × 300 次模拟，再按实际在岗时长合并结果。制造站与贸易站在相同的 4/8/12 小时节点结算；资源流默认开班已有足够周转库存，用户填写的赤金与碎片库存只用于显示库存轨迹与耗尽风险，不会把从零启动错误地建模成贸易停工。

赤金按库存流而不是最终收益处理。界面可分别填写每日任务等稳定来源、每周来源和当前库存；总净流量为“制造 + 外部来源 − 贸易消耗”，并据此估算库存可维持天数。制造站自身的赤金净流量会单独保留，消耗大于制造不会被直接判为低效。

订单品质不会直接套用峰值。PRTS 已给出 α/β 的峰值概率和分别 3/5 小时达到峰值的时间，但没有公开完整内部曲线，因此解析层对峰值前采用线性插值；快进层在每笔订单开始时按当时累计工作时间取样，换班后重置。该假设会明确显示，不会标成官方精确曲线。

## 为什么显示“保守估算”

现代后勤技能有大量跨房间状态量，例如感知信息、思维链环、人间烟火、巫术结晶、红松骑士团、设施内特定阵营人数、订单品质暖机和特殊订单。这些效果不可能只用“+X%”准确概括。

当前版本会：

- 精确处理直接效率技能；MAA 已建模技能组只辅助候选排序，不冒充精确资源流；
- 将含“每有/如果/转化/工作时长”等条件、但仅能读取直接数值部分的技能明确标为“仅计直接部分”；
- 将未完整建模的特殊技能列在警告中；
- 不把结果伪装成游戏内逐秒模拟值；
- 用满级宿舍的 `4 心情/小时` 基础恢复，按床位小时审计一班休息能否回满；审计额外计入控制中枢、会客室、办公室共 8 个辅助岗位；
- 以每日长期平均值比较方案，暂不生成两套完整且互斥的干员名单，也不模拟菲亚梅塔的心情交换。

当前“轮班与宿舍”是可持续性约束审计，不等同于完整轮班求解。控制中枢已经参与生产状态选择；下一阶段仍需把宿舍、办公室和会客室也作为可选岗位放进多班次状态求解，才能闭合依赖这些设施的人间烟火、感知信息等完整状态链。

程序会同时生成“当前 Box”和“全干员满练目录”两种机制覆盖率，而不是笼统声称整个游戏永久“全部支持”。孑的订单队列空位按界面选择的收单间隔做稳态队列期望，进行中的订单在收单时保留进度；歌蕾蒂娅的深海猎人加成会按所有已选制造站中的深海猎人总数回代一次。当前 Box 的 92 个产出相关已解锁技能均有计算路径；当前全目录覆盖为 215/275（78.2%），其余阵营、设施和特殊订单机制会继续显示为未覆盖，直到加入相应公式。

## 更新技能数据

目录中已经附带生成好的紧凑数据库。更新 MAA 和游戏数据后可重新生成：

```bash
python3 scripts/build_catalog.py \
  --building /path/to/building_data.json \
  --characters /path/to/character_table.json \
  --maa-infrast /path/to/MaaAssistantArknights/resource/infrast.json \
  --output data/catalog.json
```

游戏数据源与 MAA ResourceUpdater 保持一致，使用 `yuanyan3060/ArknightsGameResource`。PRTS 的基建、制造站、贸易站、发电站和后勤技能页面用于核对基础规则与新特殊机制。
